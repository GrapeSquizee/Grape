# 문서 이미지 개인정보(PII) 치환 파이프라인 — 프로젝트 계획

## 1. 목표

개인정보가 포함된 문서 **이미지**에서 이름, 주민등록번호, 계좌번호, 카드번호, 주소 등을
탐지하고, **임의의(합성) 값으로 교체한 이미지 + 라벨(바운딩박스/엔티티 타입)** 을 생성하여
학습용 데이터셋으로 활용한다.

- 단순 마스킹(검은 박스)이 아니라 **형태를 보존한 합성 치환**이므로, 치환 후에도 문서가
  자연스러워야 한다 (폰트/크기/배경 유사, 자릿수·하이픈 위치 보존).
- 폐쇄망(내부망) 환경에서 동작해야 하며, 외부 API·외부 다운로드에 의존할 수 없다.

## 2. 전체 프로세스 (파이프라인)

```
원본 이미지
   │
 ① 전처리          방향 보정(90°/180°) → 미세 기울기 보정(deskew) → 해상도 정규화, 노이즈 제거
   │
 ② OCR             텍스트 + 바운딩박스 추출 (오프라인 OCR 엔진)
   │
 ③ PII 탐지         [룰 기반] 주민번호·카드번호·계좌번호·전화번호 (정규식 + 체크섬)
   │               [LLM 기반] 이름·주소 등 문맥 의존 엔티티 (GPT-5.4, JSON 구조화 출력)
   │
 ④ 합성값 생성       Faker(ko_KR) + 커스텀 생성기 (유효 체크섬, 포맷/자릿수 보존)
   │
 ⑤ 이미지 치환       원본 텍스트 영역 인페인팅 → 유사 폰트/크기/색으로 합성값 렌더링
   │
 ⑥ 라벨 출력         bbox + 엔티티 타입 + 치환 텍스트 (JSON, COCO 호환 가능)
   │
 ⑦ QA 검수          Label Studio 등으로 샘플 검수 → 미탐/오탐 피드백 루프
   │
치환 이미지 + 라벨 (학습용 데이터셋)
```

### 단계별 설계 포인트

| 단계 | 핵심 결정 사항 |
|---|---|
| ① 전처리 | 회전은 두 종류를 구분해 처리: **(a) 90°/180° 방향 오류** — PaddleOCR 내장 방향 분류기(angle classifier)가 텍스트 조각 단위 180°는 자동 보정, 페이지 전체 90° 회전은 문서 방향 분류 모델(doc orientation)을 앞단에 추가하거나 "4방향 OCR 신뢰도 비교" 휴리스틱으로 판별. **(b) 미세 기울기(±10° 이내)** — OpenCV(Hough/minAreaRect)로 각도 추정 후 역회전. deskew를 안 하면 bbox가 기울어져 ⑤ 치환 렌더링이 어려워지므로 필수 |
| ② OCR | 라인 단위가 아닌 **단어/토큰 단위 bbox**가 필요 (치환 영역을 정확히 잡기 위해) |
| ③ 탐지 | 숫자형 PII는 룰이 LLM보다 정확·저렴. LLM은 이름/주소/문맥 판단에만 사용 |
| ③ 탐지 | **재현율(미탐 방지) 최우선** — 미탐 = 개인정보가 학습데이터에 유출됨. 애매하면 치환 |
| ④ 생성 | 주민번호는 유효 생년월일+체크섬, 카드번호는 Luhn 체크섬 통과하는 가짜값 생성 (학습 모델이 "유효한 형태"를 배우도록) |
| ⑤ 렌더링 | 배경색은 bbox 주변 픽셀에서 추정, 폰트 크기는 bbox 높이에서 역산 |
| ⑥ 라벨 | 원본값↔치환값 매핑 테이블은 그 자체가 개인정보 → **저장하지 않거나 별도 통제구역에 보관** |

## 3. 기술 스택

모두 **오프라인 설치 가능**(wheel + 모델 파일 반입)한 것 기준.

| 영역 | 선택 | 비고 / 대안 |
|---|---|---|
| 언어 | Python 3.10+ | 이미 보유 |
| OCR | **PaddleOCR** (korean 모델) | 한국어 인식률·단어 bbox 지원 우수. 대안: EasyOCR(설치 간단), Tesseract(kor, 품질 낮음) |
| PII 룰 탐지 | `re` + 자체 검증 로직 | 주민번호 체크섬, 카드 Luhn, 은행별 계좌 패턴 사전 |
| PII 문맥 탐지 | **GPT-5.4 내부 API** | OCR 토큰 시퀀스를 주고 엔티티 스팬을 JSON으로 받는 방식. 멀티모달 지원 여부 확인 필요(지원 시 레이아웃 이해·OCR 교차검증에도 활용) |
| 합성 데이터 | **Faker (ko_KR 로케일)** + 커스텀 Provider | 이름/주소는 Faker, 주민번호/카드/계좌는 체크섬 유효 커스텀 생성기 |
| 이미지 처리 | OpenCV (인페인팅, 전처리) + Pillow (텍스트 렌더링) | 폰트 파일(나눔고딕/맑은고딕 등) 별도 반입 필요 |
| 라벨 포맷 | JSON (COCO 스타일) | 학습 프레임워크에 맞춰 YOLO 포맷 변환기 추가 가능 |
| QA 도구 | **Label Studio** (셀프호스팅) | pip 설치 가능, 폐쇄망 동작. bbox 검수 UI 제공 |
| 파이프라인 실행 | 배치 스크립트 (초기) → 필요 시 Redis + RQ/Celery | 초기엔 단순하게, 물량 커지면 큐 도입 |

### LLM(GPT-5.4) 활용 방식

1. **엔티티 탐지**: OCR 결과(토큰 + 위치)를 프롬프트에 넣고
   `{"entities": [{"token_ids": [...], "type": "NAME|ADDRESS|...", "confidence": ...}]}`
   형태의 구조화 출력을 받음. 룰 탐지 결과와 합집합으로 사용.
2. **더블체크(선택)**: 치환 완료된 이미지의 OCR 텍스트를 다시 LLM에 넣어
   "남아있는 개인정보가 있는가"를 검증하는 2차 스크리닝 → 미탐 방어선.
3. **합성값 문맥 보정(선택)**: 주소 치환 시 문서 문맥(예: 서식 상 시/도 칸 분리)에 맞는
   형태로 생성값을 다듬는 용도.

## 4. 인프라 정리

### 현재 보유
- GPT-5.4 LLM API 엔드포인트 (내부망)
- Python 실행 환경

### 단계별 추가 필요 인프라

**Phase 1 — PoC (필수, 이것 없이는 시작 불가)**
| 항목 | 이유 |
|---|---|
| 오프라인 패키지 반입 수단 | 폐쇄망이므로 wheel 번들(`pip download`로 외부에서 수집 후 반입) 또는 내부 PyPI 미러(devpi/Nexus). **가장 먼저 확보할 것** |
| OCR 모델 가중치 파일 | PaddleOCR 한국어 detection/recognition 모델 + 방향 분류기(angle classifier) + 문서 방향 분류(doc orientation) 모델 (수백 MB) 반입 |
| 한글 폰트 파일 | 렌더링용 (나눔고딕, 나눔명조 등 OFL 폰트) |
| 샘플 문서 이미지 50~100장 | 실제 다룰 문서 유형별로 확보 (보안심의 필요할 수 있음) |

**Phase 2 — 파이프라인 구축**
| 항목 | 이유 |
|---|---|
| 작업용 서버 1대 (CPU 8코어+/RAM 16GB+) | OCR·이미지 처리 배치. GPU(예: 소형 1장)는 선택 — OCR 처리량 10배 이상 향상되나 CPU로도 가능 |
| 스토리지 (원본/산출물 분리) | 원본 이미지는 개인정보 → 접근통제된 구역, 치환 완료본은 일반 구역으로 분리 |

**Phase 3 — QA·스케일업**
| 항목 | 이유 |
|---|---|
| Label Studio 서버 (기존 서버에 동거 가능) | 검수자용 웹 UI. pip 또는 docker로 설치 |
| GPU 서버 (물량에 따라) | 수만 장 이상 처리 시 OCR 병목 해소 |
| (선택) Redis | 작업 큐. 배치 스크립트로 감당 안 될 때만 |

**Phase 4 — 운영**
| 항목 | 이유 |
|---|---|
| 감사 로그 저장소 | 어떤 이미지가 언제 처리·검수됐는지 추적 (개인정보 처리 이력) |
| 원본 폐기/보존 정책 인프라 | 치환 완료 후 원본 처리 방침에 따른 자동화 |

### GPT-5.4 API 관련 확인 사항 (내부 담당자에게 확인)
- **멀티모달(이미지 입력) 지원 여부** — 지원하면 OCR 보조·레이아웃 이해에 활용 가치 큼
- **로깅 정책** — 프롬프트에 원문 PII가 들어가므로, API 서버 측 프롬프트 로깅이 있다면 그 로그도 개인정보 통제 대상
- 구조화 출력(JSON mode / function calling) 지원 여부, 요청 처리량(rate limit)

## 5. 프로젝트 단계별 계획

| Phase | 기간(안) | 내용 | 완료 기준 |
|---|---|---|---|
| 0. 요건 정의 | 1주 | 대상 문서 유형 목록, 엔티티 정의서(무엇을 PII로 볼지), 개인정보 처리 근거·보안심의 | 엔티티 정의서 확정 |
| 1. PoC | 1~2주 | 샘플 이미지로 OCR 품질 측정, 룰+LLM 탐지 정확도 측정, 치환 렌더링 프로토타입 | 탐지 재현율 ≥ 95%(샘플 기준), 렌더링 육안 통과 |
| 2. 파이프라인 구축 | 2~4주 | 모듈화(전처리/OCR/탐지/생성/렌더링/라벨), 라벨 포맷 확정, 배치 실행기 | 100장 무인 배치 처리 성공 |
| 3. QA 루프 | 2주+ | Label Studio 검수 → 미탐/오탐 분석 → 룰·프롬프트 개선 반복, 2차 LLM 스크리닝 도입 | 검수 통과율 목표 도달 (예: 미탐 0건/1,000장) |
| 4. 스케일·운영 | 지속 | 전체 물량 처리, 감사 로그, 원본 폐기 정책 적용 | 운영 절차서 확정 |

## 6. 주요 리스크와 대응

| 리스크 | 대응 |
|---|---|
| OCR이 못 읽는 텍스트(도장 겹침, 손글씨, 저해상도) 속 PII 미탐 | 2차 LLM 스크리닝 + 사람 샘플 검수. 손글씨 비중이 크면 손글씨 인식 모델 추가 검토 |
| LLM 오탐/미탐 (이름·주소 경계 판단 실패) | 룰과 합집합 사용, confidence 낮은 건 사람 검수 큐로 |
| 치환 매핑 테이블 자체가 개인정보 | 기본 정책: 매핑 미저장. 필요 시 암호화 + 접근통제 구역 보관 |
| 프롬프트를 통한 PII의 LLM 서버 유입 | 내부망 API이므로 허용 범위 확인, 서버 측 로깅 정책 점검 |
| 폐쇄망 패키지 반입 지연 | Phase 0에서 전체 의존성 목록(wheel + 모델 + 폰트)을 한 번에 수집해 일괄 반입 |

## 7. 저장소 구조 (안)

```
grape/
├── docs/                # 계획서, 엔티티 정의서
├── src/
│   ├── preprocess/      # 이미지 전처리
│   ├── ocr/             # OCR 래퍼
│   ├── detect/          # 룰 탐지 + LLM 탐지
│   ├── synth/           # 합성값 생성 (Faker + 커스텀)
│   ├── render/          # 인페인팅 + 텍스트 렌더링
│   └── pipeline.py      # 배치 실행기
├── configs/             # 엔티티 정의, 은행 계좌 패턴, 프롬프트 템플릿
├── fonts/               # 반입한 폰트
└── tests/               # 체크섬 생성기, 룰 탐지 단위테스트
```
